# 页码解析 主计划（Master Plan）

> 状态：**已批准（2026-08-29）**，进入实施
> 目标：实现按页解析进度，与文件级整体进度彻底分离

## 一、背景与问题

当前版本对页码解析未实现，用文件数量替代页码，导致单个多页 PDF 的进度条全程显示"第 1/1 份 100%"，效果很差。

**实际场景调研结论**：
- 引擎状态 API（`fast_api.py`）只返回 `status` / `queued_ahead`，**不含页码字段**；
- 页码唯一来源是引擎日志 `_data/logs/engine.log`，其中包含：
  - `Pipeline processing-window multi-file run. doc_count=1, total_pages=4, window_size=64, total_batches=1` → 本次任务总页数
  - `Pipeline processing window batch 1/1: 4/4 pages, batch_pages=4, doc_slices=doc0:1-4` → 每批边界累计页进度
  - `Processing pages: 75%|...| 3/4 [...]`（tqdm 逐页累计）→ 最细粒度逐页进度
- 现有 `EngineStageTracker` 只提取阶段文案（如"页面批量分析 1/1"），**丢失页码数字**；
- 引擎强制串行（`MINERU_API_MAX_CONCURRENT_REQUESTS=1`），任何时刻至多一个任务处于 `processing`，页码可安全归属给当前解析中任务。

## 二、设计原则（用户明确要求）

**页码是对文件的进度；文件数量是整体的进度，不得混为一谈。**

| 位置 | 维度 | 显示 |
|------|------|------|
| 顶部整体汇总 | 文件级（整体） | `已完成 a / N 份` |
| 处理中任务卡 | 页级（单文件） | `第 X / Y 页` |
| 排队任务卡 | — | `排队中` / 前面还有 n 个 |
| 完成任务卡 | — | `完成` |

约束：
1. 顶部汇总永不混入页码；任务卡进度永不用文件数；单位必须明确标注（"份" vs "页"）。
2. 页码只在文件进入 `processing` 时出现。
3. 页进度只归属当前解析中的那一个任务。

## 六、边界与兜底

| 场景 | 处理 |
|------|------|
| 图片/单页文件 | total_pages=1；无页码数据则显示"解析中"文本 |
| max_pages 截断 | 引擎 total_pages 即实际处理页数，无需处理 |
| 引擎冷启动/排队 | 无 run 日志 → 保持排队提示，不显示页码 |
| 相邻任务切换竞态 | 进入 processing 时归属、离开时清理；残留 ≤0.8s 轮询间隔，仅展示层瞬时抖动，可接受 |
| 日志轮转/截断 | 复用现有 size 检测机制 |
| 引擎空闲释放 | detach 时清空页码，空闲不显示 |

## 七、验证方式

不重启整套环境，仅重启 WebUI；用 TRAE-browseruse 提交真实 PDF 观察进度条逐页变化（沿用既有 WebUI 冒烟方案，不引入 playwright）。
