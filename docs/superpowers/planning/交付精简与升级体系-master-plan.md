# 交付精简与升级体系 主计划（Master Plan）

> 状态：**待批准 → 已批准（2026-09-03，用户逐项拍板）**，进入实施
> 目标：小白用户只拿一个 exe 即可完整部署；组件清单全程可见；多源竞速下载；支持从远程仓库修复/升级

## 一、背景与问题

当前安装器存在四类问题（用户 2026-09-03 提出）：

1. **交付形态错误**：安装器把 `src/webui`、`src/tray`、`scripts/*.py` 整个复制到安装目录——用户拿到的是"半个项目仓库"而非一个工具。安装的意义是：**只有** **`MinerU安装.exe`** **一个文件即可完整部署**，安装目录应只含 环境/模型/启动程序，不暴露源码。
2. **过程黑盒**：装了什么、缺什么、正在装什么，用户不可见。
3. **单源单线程**：固定阿里源，`torchvision (8.9MiB)` 卡住只能干等；模型下载只有 modelscope 单源。
4. **无修复/升级通道**：文件损坏只能全量重装；无版本管理。

## 二、设计原则（用户已拍板的决策）

| #  | 决策      | 内容                                                                               |
| -- | ------- | -------------------------------------------------------------------------------- |
| D1 | 源码保护方式  | **应用源码内嵌 exe（onedir 模式，非单文件）**——启动速度优先；Python 源码以字节码（.pyc / PYZ）形式分发，不以明文 .py 落盘 |
| D2 | 卸载器     | 本期一起做                                                                            |
| D3 | 下载线程数   | 默认 **16**，可设置范围 **4–64**，持久化                                                     |
| D4 | 测速策略    | 探针约 5 秒；**全部慢则用最快的兜底**——绝不出现"全部停滞 >30s 后不下载"，任何时刻至少有一条活跃下载流                      |
| D5 | 实施顺序    | 1（交付精简+卸载）→ 2（组件清单）→ 3（多源下载）→ 4（远程发布/修复/升级）                                      |
| D6 | 远程仓库    | 最终版本打包上传用户 GitHub 仓库 `SL-thirdparty/mineru-mod`；后续损坏/升级直接拉取对比文件                  |
| D7 | push 纪律 | 项目记忆约束"禁止自动 push"仍然有效——本计划 P4 的推送是**用户显式授权的例外**，且推送前必须向用户展示将推送的内容清单              |

### 目标安装目录形态（P1 后）

```
C:\MinerU_App\
├── MinerU文档解析\              ← onedir 启动器（无解压开销，秒启）
│   ├── MinerU文档解析.exe        ← 托盘启动器（tray 源码在 PYZ 字节码中）
│   └── _internal\
│       ├── ...                   ← PyInstaller 运行时
│       └── webui\
│           ├── app.pyc           ← WebUI 编译字节码（源码不落盘）
│           └── static\           ← 浏览器端资源（html/js/css/字体，本就是公开资源）
├── runtime\
│   ├── venv\                     ← 依赖环境（GPU 自适应 torch 在安装期决策，方案不变）
│   └── models_cache\             ← 2.42GB 模型
├── 使用说明.html
└── 卸载MinerU.exe
```

对比现状：`src/`、`scripts/`、`release/mineru_tray/` 全部消失。

**技术可行性（已核实）**：`src/webui/app.py` 为单文件入口（75.6KB，无本地包导入），static 按 `Path(__file__)` 相对定位——`venv\python.exe app.pyc` 直跑字节码完全兼容，static 与 .pyc 同目录即可。启动器不再查找 `src/webui/app.py`，改为查找 `runtime/venv`；`MINERU_ROOT` 环境变量由启动器显式传入（规避目录层级变化对 `ROOT` 推导的影响）。

## 六、边界与兜底

| 场景             | 处理                                                   |
| -------------- | ---------------------------------------------------- |
| 反编译 .pyc       | 接受。目标是防小白误改/明文暴露，非对抗逆向工程；static 本就是浏览器端公开资源          |
| onedir 体积膨胀安装器 | 安装器 onefile 压缩后预计 55-65MB（现 39.9MB），可接受              |
| `.pyc` 版本兼容    | venv 恒为 3.11（安装器强制），与构建机同 minor 版本，字节码兼容；构建脚本校验解释器版本 |
| 更新时文件占用        | 暂存 `.update/` → 托盘退出+子进程终止 → 换文件 → 重启；失败回滚暂存         |
| GitHub 国内不可达   | 镜像链 ghproxy/jsdelivr 逐级回退；全部失败→提示手动下载安装器             |
| 测速全部失败         | 按固定优先序（阿里→清华→中科大→腾讯→官方）直连，不因测速失败而中止                  |
| 停滞换源仍失败        | 单文件重试 3 次（现有逻辑）+ 源轮转；最终明确报错并列出失败文件清单                 |
| venv 修复        | 不远端拉文件重建（venv 内含绝对路径），由安装器修复模式重建；模型按 sha256 校验重下     |
| 推送纪律           | main 源码推送与 dist/Release 发布均需先向用户展示清单（D7，显式授权的例外）     |
